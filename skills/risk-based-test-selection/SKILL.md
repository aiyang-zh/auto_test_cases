# 风险导向选测（最优测试量）

## R — 核心原则 (Reading)

> 软件测试员要学会的一个关键思想是，如何把数量巨大的可能测试减少到可以控制的范围，以及如何针对风险做出明智的抉择，哪些测试重要，哪些不重要。我们的目标是找到最优的测试量，使测试不多不少。

---

## I — 方法论骨架 (Interpretation)

完全测试因输入、输出、路径与说明书主观性共同爆炸而不可能；任何删减都已是不完全测试，因此停测本身就是冒险。

核心动作不是“再多测一点”，而是显式风险管理：承认必须抽样 → 按后果与可能性给候选测试排序 → 在费用陡增与漏缺陷收益递减之间找“最优测试量”。

测少了漏大量缺陷；测多了费用暴涨而漏测不再显著下降。放行依据应是剩余风险可接受，而不是“用例跑完了”。

---

## A1 — 典型应用 (Past Application)

### 案例 1: Windows 计算器加法
- **问题**: 合法数、非法键入、多操作数组合爆炸，穷尽加法不可能。
- **做法**: 经典示例用计算器证明：剔除“重复/无必要”条件即不完全测试；测试员必须学会压缩可能并按风险抉择。
- **结论**: 目标是可控范围内的最优测试量，而非穷尽。
- **结果**: 为后续设计与选测技术铺垫——技术服务于风险抽样，不是证明全覆盖。

### 案例 2: 迪斯尼《狮子王》配置灾难（反面）
- **问题**: 只在开发机等极少数友好配置上验证就大规模发货。
- **做法**: 说明“错误地确定测试对象”——抽样偏差等于选错风险焦点。
- **结论**: 风险导向选测必须覆盖真实用户环境矩阵，不能只测开发机。
- **结果**: 节假日支持灾难与召回费用吞噬利润。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 上线前时间不够，自动化/手工用例堆成山，问“还能砍什么 / 何时停”。
2. 组合爆炸（配置×输入×路径）明显，不知如何抽样仍可控风险。
3. 管理层要求“测完再发”，需要用最优测试量曲线做沟通框架。
4. 微服务/回归套件过大，要按业务风险重排优先级。

### 语言信号 (用户的话里出现这些就应激活)

- "测不完 / 何时停测 / 还要测什么"
- "optimal test amount / risk-based testing / stop testing"
- "用例太多怎么砍 / 回归怎么排优先级"
- "完全测试不可能怎么办"

### 与相邻 skill 的区分

- 与 `prove-presence-not-absence` 的区别: 本 skill 回答“选哪些测、何时停”；彼 skill 回答“通过后能宣称什么（不能证无）”。
- 与 `equivalence-and-boundaries` 的区别: 彼 skill 是压缩输入空间的具体技法；本 skill 是更高层的风险排序与止损决策。
- 与 `pesticide-paradox` 的区别: 彼 skill 处理“旧套件免疫”；本 skill 处理“首轮/当前批次测什么”。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **框定爆炸面**
   - 列出主要输入维、输出维、路径/状态、环境配置。
   - 完成标准: 用户认可“不可穷尽”的维度清单（至少 2 维）。

2. **按风险给候选测试打分**
   - 维度建议: 用户影响、出现频率、历史缺陷密度、法规/资金安全、修复成本。
   - 完成标准: 有一份高/中/低风险测试清单（可粗分）。

3. **砍低价值类并声明剩余风险**
   - 明确不测什么、为何可接受；写出停测条件（时间窗、风险阈值、关键路径绿）。
   - 完成标准: 放行说明含“已测焦点 + 未测风险”，而非“已完全测试”。
   - 判停条件: 若用户其实要的是具体字段取点，跳到 `equivalence-and-boundaries`。

4. **必要时叠技法**
   - 高风险区用等价类/边界、成群跟进、换手法等兄弟 skill 加深。
   - 完成标准: 高风险项都有对应设计手法，不只是口号“重点测”。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 用户只要某字段的边界/等价类取点清单（用 `equivalence-and-boundaries`）。
- 用户在纠正“测过了=没 bug”的表述（用 `prove-presence-not-absence`）。
- 安全关键系统要求形式化证明或极高完整性时——本框架是商业风险取舍，不是安全证明论。

### 常见失败模式

- 只测“应能跑通”的 happy path，漏掉集成与异常路径（火星登陆者式确认偏误）。
- 配置抽样极窄却全量发货（《狮子王》）。
- 把“用例跑完 / 自动化全绿”当成完备质量证明。

### 适用边界与局限

- 早期语境约 2000 年代桌面/早期 Web、客户端安装为主；对持续交付、微服务、金丝雀、feature flag、可观测性等现代止损手段着墨不足。
- “项目终将发布、必须在某点停测”默认商业软件；强合规/安全关键系统可能需要不同停测伦理。

### 容易混淆的邻近方法论

- 缺陷 triage（并非所有缺陷都修）——相关但焦点是修不修，不是测不测。
- 代码覆盖率目标——覆盖是手段线索，不能替代风险排序。
