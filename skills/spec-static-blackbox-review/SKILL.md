# 说明书静态黑盒审查

## R — 核心原则 (Reading)

> 测试产品说明书的第一步不是马上钻进去找缺陷，而是站在一个高度上进行审查。……如果能够很好地理解产品说明书后的诸多为什么和怎么做，就可以更好地进行细节检查。

> 如果审查产品说明书的某一部分时不理解，不要假定它是对的而把它放掉。……最好现在就搞懂。

---

## I — 方法论骨架 (Interpretation)

静态黑盒 = 不运行产品、也不看实现，只审查“期望是什么”。说明书（或口头/脑中的规格）就是最早、最便宜的缺陷现场。

审查分两层：
1. **高空**：客户是谁、要解决什么、对照标准/规范与竞品，抓根本遗漏与错误假设。
2. **低空**：用 8 属性（完整、准确、精确清晰、一致、贴切、合理、代码无关、可测试）+ 问题用语清单抠措辞与可测性。

读不懂 ≠ 先跳过；读不懂往往就是缺陷。确认（符合说明书）之前，先质疑说明书本身是否值得验证（validation）。

## A1 — 典型应用 (Past Application)

### 案例 1: 哈勃主镜——确认通过、验证失败
- **问题**: 镜子按产品说明精密加工并通过对照说明的测试，上天后无法正确聚焦。
- **做法**: 说明书本身错了；只做确认不做验证会系统性保证错误产品。
- **结论**: 绝不能假定产品说明书是对的；静态审查必须挑战规格。
- **结果**: 1993 年航天飞机任务安装校正装置才修复成像。

### 案例 2: Windows 计算器说明书摘录
- **问题**: 短说明书看似清楚，却可能缺边界、错误处理与可测判据。
- **做法**: 先当客户理解“为什么”，再用属性/用语清单找绝对词、模糊词与不可量化词。
- **结论**: 格式无关，核心是高空→低空的审查顺序。
- **结果**: 后续动态黑盒用例有可靠期望可对照。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 拿到 PRD/需求文档，要做评审或写评审意见
2. 问「还没代码怎么开始测」「说明书从哪查」
3. 规格含糊（“快速”“有时”“等等”），争论算不算缺陷
4. 担心需求遗漏目标环境、安全或行业标准

### 语言信号 (用户的话里出现这些就应激活)

- 「帮我审一下这份 PRD / 需求说明书」
- 「静态黑盒 / 说明书审查 / spec review」
- 「这些需求可测吗 / 问题用语」
- 「complete accurate testable specification」

### 与相邻 skill 的区分

- 与 `exploratory-testing` 的区别: 本 skill 面向**有（或可写出）规格文档**的审查；无书面规格、只能边用边学时用探索测试。
- 与 `equivalence-and-boundaries` 的区别: 本 skill 找**期望本身的洞**；后者在期望已定后设计输入抽样与边界用例。
- 与 `four-quadrant-technique` 的区别: 四象限回答“选哪类技术”；本 skill 是静态黑盒象限的具体执行清单。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **确认审查对象与形态**
   - 完成标准: 标明书面说明书 / 口头规格 / 需访谈补全；列出客户与主要目标。
   - 判停条件: 若完全无任何可访问的期望来源，跳到建议启用 `exploratory-testing`。

2. **高空审查（根本问题）**
   - 完成标准: 从客户视角列出 3+ 个“为什么/怎么做”；对照适用标准/规范与至少 1 个竞品或类似产品；记下遗漏与冲突假设。

3. **低空审查（属性 + 用语）**
   - 完成标准: 对文档抽检对照 8 属性；标出问题用语（总是/有时/等等/迅速/如果—那么缺 else 等）并写成可操作的缺陷条目（缺什么、为何不可测、建议澄清问句）。

4. **输出评审包**
   - 完成标准: 按严重度排序的规格问题列表 + 需产品方确认的问题清单；注明哪些问题会阻断后续用例设计。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 任务是对着已发布构建做功能摸底、且无规格可审 → `exploratory-testing`
- 任务是为已清晰字段设计等价类/边界数据 → `equivalence-and-boundaries`
- 纯代码审查（静态白盒）——本 skill 不看实现

### 常见失败模式

- 只做确认、不做验证：按错误说明书精密“测过”仍交付失败（哈勃）
- 读不懂就假定说明书对，把缺陷推迟到编码后才暴露
- 说明书从未最终版却当冻结真理（变更未重审）

### 适用边界与局限

- 常见示例偏桌面/Windows 说明书与 GUI 标准；现代 API 契约、OpenAPI、用户故事 backlog 需把同一清单映射到新载体
- 对敏捷“轻文档”场景，实践中常假设总能问出“脑中说明书”；极端无对接人时效力下降
- 强合规行业的正式需求基线流程，传统材料着墨少于商业产品经验

### 容易混淆的邻近方法论

- 需求工作坊 / 用户故事映射：偏共创产品；本 skill 偏**测试员视角的缺陷查找**
- 代码 review：静态白盒，不是静态黑盒
