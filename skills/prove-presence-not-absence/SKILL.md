# 只能证有、不能证无

## R — 核心原则 (Reading)

> 软件测试工作与防疫员的工作极为相似，可以报告软件缺陷存在，却不能报告软件缺陷不存在。你可以进行测试，发现并报告软件缺陷，但是任何情况下都不能保证软件缺陷没有了。

---

## I — 方法论骨架 (Interpretation)

测试在逻辑上像检疫：找到害虫痕迹可断定“有”；搜不到只能说“在此搜索下未找到活虫”，除非把房子拆掉，否则不能保证没有漏网。

因此，一批（甚至大量）用例通过，只支持存在性结论的否定形式——“这些探针未击中缺陷”——绝不支持“产品无缺陷”的完备证明。

沟通与放行必须把“测过了”翻译成“已执行范围 + 未覆盖风险”，把停测说成风险管理决策，而不是质量完备证书。

---

## A1 — 典型应用 (Past Application)

### 案例 1: 检疫员搜房类比
- **问题**: 一间房找不到活害虫迹象，能否宣称无害虫？
- **做法**: 该类比对比“找到痕迹→有”与“找不到→仅本次搜索未发现”。
- **结论**: 测试同理——能证有，不能证无；继续测才可能再找到。
- **结果**: 确立测试认识论边界，约束后续所有放行话术。

### 案例 2: 计算器穷尽不可能（配套）
- **问题**: 有人仍相信“测够了就能保证没有缺陷”。
- **做法**: 与穷尽不可能原则组合：穷尽不可能 → 任何停测都留盲区 → 更不能声称证无。
- **结论**: “完全测试 / 无缺陷”表述既不可行也不诚实。
- **结果**: 为风险导向停测提供哲学底座。

---

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 发布评审有人说“QA 测过了，保证没问题”。
2. 客户/老板要求“证明没有 bug 再上线”。
3. 测试报告草稿写了“已完全测试 / 无缺陷”。
4. 需要向非测试干系人解释为何绿条不等于零风险。

### 语言信号 (用户的话里出现这些就应激活)

- "测过了就没 bug / 证明没有缺陷"
- "fully tested / no bugs / prove there are no bugs"
- "可以保证质量吗 / 零缺陷发布"
- "测试通过是不是就安全了"

### 与相邻 skill 的区分

- 与 `risk-based-test-selection` 的区别: 彼 skill 教如何选测与停；本 skill 教停测后能说什么、不能说什么。
- 与 `pesticide-paradox` 的区别: 彼 skill 解释为何同一套绿测仍可能漏障；本 skill 是更一般的证伪边界。
- 与 `bug-cluster-heuristic` 的区别: 彼 skill 在已发现缺陷后加码搜索；本 skill 不依赖是否已找到缺陷。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **抓住越界表述**
   - 标出“完全测试 / 无缺陷 / 保证质量 / prove absence”等句子。
   - 完成标准: 至少标出 1 处需要改写的承诺。

2. **用检疫类比重写结论**
   - 改为：“在范围 X 的测试下未发现 / 发现了 Y”；附未测风险。
   - 完成标准: 结论句可被逻辑上诚实的干系人复述。

3. **把停测接回风险管理**
   - 询问：剩余风险谁接受？关键路径是否已覆盖？是否需换手法再探？
   - 完成标准: 给出放行/继续测的二选一建议及理由。
   - 判停条件: 若用户要具体砍用例清单，转 `risk-based-test-selection`。

---

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 用户问的是等价类怎么划、边界取哪几个点。
- 用户明确要排风险优先级砍回归（主调 `risk-based-test-selection`）。
- 用户要的是形式化验证 / 数学证明无缺陷——超出本 skill 范围。

### 常见失败模式

- 相信“测完了=没有缺陷”，据此过度承诺或过早停测。
- 报告或口头使用“已完全测试 / 无缺陷”。

### 适用边界与局限

- 早期桌面/Web 语境下，放行多靠人工测试结论；未充分讨论现代工程系统（类型系统、CI、金丝雀、可观测性）如何改变“证明”的社会过程——但“测试不能证无”的逻辑边界仍然成立。

### 容易混淆的邻近方法论

- 确认 vs 验证（符合说明书 ≠ 满足用户需求）——另一类“测过了仍失败”。
- 杀虫剂现象——绿测免疫是证无幻觉的常见机制之一，但不是全部。
