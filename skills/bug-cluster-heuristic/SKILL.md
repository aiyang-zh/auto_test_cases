# 缺陷成群启发式

## R — 核心原则 (Reading)

> 软件缺陷往往成群出现：发现一个，附近很可能还有更多。不要把首个缺陷当成孤立事件收工。

---

## I — 方法论骨架 (Interpretation)

发现一处缺陷后，不要当孤立事件收工。默认“附近”还有更多——附近可以是同模块、同程序员习惯区、或同一设计/体系根因的不同表象。

机制包括：程序员状态波动、个人重复犯错模式、以及表面无关缺陷共享深层根因（冰山一角）。

反向也成立：长时间怎么找都找不到，可能代码确实较干净——启发式用于动态调整注意力，不是数学定律。

---

## A1 — 典型应用 (Past Application)

### 案例 1: 害虫成群类比与三因解释
- **问题**: 为何常常很久找不到，一找到就接二连三？
- **做法**: 用心情波动 / 重复习惯 / 冰山根因三类解释，指导加大局部强度。
- **结论**: 找到越多，越应怀疑该区域还有更多。
- **结果**: 成为动态调整测试投入的核心启发式。

### 案例 2: 已找到缺陷的地方再找
- **问题**: 若在不同特性中大量发现上边界缺陷，下一步投哪？
- **做法**: 对所有特性加重上边界测试，确认问题是否普遍。
- **结论**: 成群模式应推广到同类边界/同类操作。
- **结果**: 用已发现模式驱动下一轮用例，而不是均匀撒网。

---

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 刚报了一个 bug，纠结是继续深挖该模块还是换功能。
2. 同一作者/同一服务短时间多单连爆。
3. 表面不同的缺陷开始像同一设计缺陷的分身。
4. 长时间零发现，不确定是质量好还是测错地方。

### 语言信号 (用户的话里出现这些就应激活)

- "缺陷成群 / bug cluster / 附近还有没有"
- "这个模块连着爆 / 要不要继续挖"
- "找到一个要不要加大测试"
- "测试注意力投哪 / where to dig next"

### 与相邻 skill 的区分

- 与 `pesticide-paradox` 的区别: 成群是空间/根因上的加码；杀虫剂是时间上旧探针失效。
- 与 `risk-based-test-selection` 的区别: 全局风险排序 vs 局部发现后的再分配。
- 与 `equivalence-and-boundaries` 的区别: 技法提供“怎么测同类边界”；成群决定“把技法加在哪片区域”。

---

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **定位“附近”**
   - 从已发现缺陷抽出：模块、作者、输入类、边界类型、状态、共享依赖。
   - 完成标准: 写下 2–4 个可搜索的邻近轴。

2. **加码局部搜索**
   - 在邻近轴上增加用例/探索会话；同类边界推广到其他特性。
   - 完成标准: 有具体加测清单，且说明相对全局的优先级上调理由。

3. **检查冰山根因**
   - 问：这些缺陷是否可能共因？若是，推动设计/评审而不只是逐个修表象。
   - 完成标准: 标明“孤立缺陷 / 疑似共因”及建议动作。
   - 判停条件: 若长期零发现且覆盖合理，可下调该区强度，回到全局风险排序。

---

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 还没有任何缺陷线索，只是初次规划测什么（用风险选测）。
- 问题是旧套件绿但仍漏障（先考虑杀虫剂）。
- 把成群当成铁律，导致在低价值模块无限深挖而忽略未测高风险区。

### 常见失败模式

- 找到一个就收工，不检查附近。
- 反面：若怎么找都找不到，也可能真的很少——不要为了“成群”硬造缺陷。

### 适用边界与局限

- 在高度自动化生成代码、微服务强隔离场景，“附近”要重映射到服务边界与契约，不能机械按“同一个模块文件”理解。
- 被当作准规律时可能造成局部过度测试。

### 容易混淆的邻近方法论

- 杀虫剂怪事、风险导向选测、等价类中的边界优先。
