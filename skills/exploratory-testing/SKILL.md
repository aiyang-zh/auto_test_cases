# 无说明书时的探索测试

## R — 核心原则 (Reading)

> 此时可以采取称为探索测试的解决方案——了解软件、设计测试、执行测试同时进行。这就需要把软件当做产品说明书来对待。……运用静态黑盒技术，把软件当成说明书来分析，然后运用动态黑盒技术进行测试。

> 在这种情况下，无法像有产品说明书那样完整测试软件……无法断定是否遗漏功能，但是可以系统地测试软件，找到软件缺陷几乎是肯定的。

---

## I — 方法论骨架 (Interpretation)

探索测试不是瞎点，而是**学习—设计—执行并行**的权宜流程：把正在运行的软件当作“活说明书”，先系统记下它声称能做什么，再用静态黑盒思路审这份“自述”，再用动态黑盒手法压它。

约束要诚实：没有外部期望时，你很难证明“该有却没有的功能”；你仍可系统找崩溃、矛盾、难用与错误处理失败。优先通过性路径摸清地图，再做失效性施压。产出应是可复用的功能笔记 + 缺陷，而不是一次性随手点。

---

## A1 — 典型应用 (Past Application)

### 案例 1: 大爆炸 / 边写边改无说明书
- **问题**: 成熟过程应有详细说明；大爆炸或松散边写边改时常没有可依文档。
- **做法**: 边用边记功能，把软件当说明书做静态黑盒式分析，再套动态黑盒。
- **结论**: 非理想但可行；不能宣称完备，尤其无法断言遗漏功能。
- **结果**: 仍可稳定发现缺陷，并逼项目方补细节（“这是我准备测和提缺陷的内容”）。

### 案例 2: 与有说明书路径对照
- **问题**: 有说明书时可完整对照期望；无说明书时失去“遗漏功能”判据。
- **做法**: 明确降低完备性主张，把精力放在已暴露行为的系统覆盖与风险点。
- **结论**: 探索是适应，不是替代正式规格流程的理想态。
- **结果**: 测试员保留专业产出（记录、缺陷），避免假装“已按规格测完”。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 接手遗留系统，文档缺失或严重过时
2. 原型/大爆炸交付，只有可运行构建
3. 问「没有需求怎么设计测试」「边探索边记」
4. 规格口头存在但拒绝写文档，需要先摸清再对齐

### 语言信号 (用户的话里出现这些就应激活)

- 「没有说明书 / PRD 怎么测」
- 「探索测试 / exploratory testing」
- 「遗留系统摸一遍」「边学边测」
- 「大爆炸 / 边写边改」

### 与相邻 skill 的区分

- 与 `spec-static-blackbox-review` 的区别: 有文档先审文档；本 skill 是**无文档时把软件当文档**。
- 与 `equivalence-and-boundaries` 的区别: 探索中可局部用等价/边界，但触发点是“无规格地图”；一旦地图稳定，用例精炼交给后者。
- 与 `pesticide-paradox` 的区别: 杀虫剂现象是**旧手法失效要换招**；探索是**缺规格时的起步模式**，不是专门治免疫回归。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **声明局限与目标**
   - 完成标准: 书面说明无法断言遗漏功能；目标是系统发现缺陷并产出功能地图。

2. **学习并记录“活说明书”**
   - 完成标准: 按界面/入口逐项列出功能、可见状态、明显规则；标注未知与矛盾。

3. **对记录做静态黑盒式分析**
   - 完成标准: 用完整性/一致性/可测性等视角标出自相矛盾、模糊行为、缺错误处理；生成待澄清问题给项目方。

4. **动态黑盒施压（先通过后失效）**
   - 完成标准: 先覆盖主路径通过性；再对高风险点做边界/无效/空值等失效性尝试；缺陷写成可再现步骤。
   - 判停条件: 若中途拿到正式说明书，切换/组合 `spec-static-blackbox-review` 对照补测遗漏功能。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 已有可审的 PRD/说明书且任务是评审规格 → `spec-static-blackbox-review`
- 字段规则已清晰，只需造等价类与边界表 → `equivalence-and-boundaries`
- 需要证明“没有缺陷”或发布签字完备性——探索做不到

### 常见失败模式

- 把探索当成随意点点，不记录、不系统
- 无说明书却宣称“已完整测试 / 无遗漏功能”
- 只测“应能跑通”而漏掉缺陷（火星登陆者式确认偏误）

### 适用边界与局限

- 常见探索实践偏单机桌面黑盒；现代会话式探索（charter、时间盒、配对）与可观测性驱动探索需当代补丁
- 对强监管“必须有追溯规格”的项目，探索只能作补充，不能替代正式基线
- 微服务/契约测试时代，“无文档”常有 OpenAPI/事件契约可审——应先找这些伪说明书

### 容易混淆的邻近方法论

- Ad hoc testing：无结构乱点；本 skill 要求记录与技术复用
- Session-based exploratory testing（当代实践）：同精神，早期表述未用该术语
