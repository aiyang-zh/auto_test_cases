# 需求 → 测试用例（编排）

把常见测试设计方法串成一条可执行流水线：**给需求，出用例，并写入 Markdown 文档**。
默认按黑盒（有说明书/需求文本）设计；无需求细节时降级为探索测试清单（同样写 md）。

## 何时调用

- 用户粘贴需求、用户故事、接口字段、规则说明，并要测试用例 / 测试点
- 用户说「根据这个功能帮我写测试」「覆盖边界和异常」「写到 md 里」

## 何时不调用

- 只有抽象理论问答（改用单一方法论 skill）
- 用户只要缺陷报告模板（`professional-bug-reporting`）
- 用户只要自动化代码且已有用例表

---

## 交付硬性要求（必须遵守）

1. **必须用 Write/Edit 工具把完整内容写入 `.md` 文件**，不能只在对话里贴一版表格就结束。
2. 对话里只需简短汇报：**文件路径 + 用例条数 + 待确认问题数**；详细内容以 md 为准。
3. 路径规则（用户未指定时）：
   - 默认目录：`docs/testcases/`（不存在则创建）
   - 默认文件名：`TC-<模块英文或拼音短名>-YYYYMMDD.md`
     例：`docs/testcases/TC-guild-stall-buy-20260729.md`
   - 用户若指定路径/文件名，以用户为准；可覆盖更新同一文件。
4. 文件开头必须有元信息（见下方模板）。

---

## 执行步骤（必须按序）

收到需求后，**不要直接瞎列用例**。按下面 6 步设计，再写入 md。

### 1. 澄清与静态审查（说明书视角）

从需求文本提取：

| 项 | 内容 |
|---|---|
| 被测对象 | 功能/接口/页面名 |
| 角色与前置 | 谁、什么状态可操作 |
| 输入 | 字段、类型、范围、必填 |
| 规则 | 业务规则、校验、权限、状态机 |
| 输出/副作用 | 成功结果、失败提示、写库/发消息 |
| 歧义/缺口 | 看不懂、矛盾、未定义（列出问题，可边标边出用例） |

对歧义：**不要假装需求完整**。标注「假设：…」或「待确认：…」，仍可基于合理假设出用例。

完成标准：能用一句话复述「谁在什么条件下对什么输入得到什么结果」。

### 2. 划范围与风险（决定测什么）

用风险把点排优先级（P0/P1/P2）：

- **P0**：资金/安全/主路径核心、数据丢失、权限绕过
- **P1**：常见分支、重要校验、兼容关键路径
- **P2**：罕见组合、文案、边缘体验

写 3～7 条「本次必测 / 可砍」说明。时间紧则先只交 P0+P1。

完成标准：有优先级，不是无差别穷举。

### 3. 等价类划分

对每个关键输入/规则：

1. 划 **有效类** / **无效类**（必要时再细分）
2. 每类写 **代表值**（1 个即可，除非类内行为可能不同）
3. 标明 **通过性**（正常能用）还是 **失效性**（应正确拒绝）

完成标准：每个关键字段至少有有效代表 + 无效代表。

### 4. 边界与次边界

对数值、长度、枚举、日期、数量等：

- 合法区内边界（min、max）
- 刚越界（min-1、max+1）
- 空 / 默认 / 零 / 仅空白
- 次边界（若相关）：2 的幂长度、特殊字符、编码边界等

完成标准：有边界用例，不只是「正常一条 + 随便异常一条」。

### 5. 场景与状态（如适用）

若需求含状态/流程（下单、审批、登录会话）：

- 主成功路径（端到端 1～3 条）
- 关键非法转换 / 重复提交 / 中断恢复
- 权限：有权 / 无权 / 越权

完成标准：不只测单字段，覆盖主路径。

### 6. 写入 Markdown 文件（固定格式）

将完整文档写入目标 `.md`（见「交付硬性要求」）。用例表每条至少含：

| 用例ID | 标题 | 优先级 | 类型 | 前置条件 | 步骤 | 输入数据 | 预期结果 | 等价类/边界说明 | 假设/待确认 |
|---|---|---|---|---|---|---|---|---|---|

约定：

- **类型**：功能 / 边界 / 异常 / 权限 / 状态 / 兼容（可选）
- **用例ID**：`TC-<模块缩写>-001` 递增
- 步骤简短可执行；预期结果可判定（含提示文案/状态码/数据变化）
- 文末必须有：**覆盖摘要** + **未覆盖与风险** + **待产品确认问题列表**

## 数量经验

- 小功能（1～3 字段）：**8～20** 条
- 中等功能：**15～40** 条（先交 P0+P1）
- 禁止为凑数重复同等价类；禁止只有 Happy Path

## 边界

- 需求为空或只有一句口号 → 先追问最小输入/输出/规则，或写入探索测试清单 md
- 安全/合规强制全量 → 标明不能随意砍 P2，改为标注合规必测项
- 时代/项目差异 → 用例字段可按团队模板微调列名，但必须保留：步骤、数据、预期、优先级
- **禁止**只在聊天回复用例而不落盘 md
