# 杀虫剂怪事（换手法）

## R — 核心原则 (Reading)

> Boris Beizer……杜撰了“杀虫剂怪事”一词，用于描述软件测试越多，其对测试的免疫力越强的现象。……为了克服杀虫剂怪事，软件测试员必须不断编写不同的、新的测试程序，对程序的不同部分进行测试，以找出更多软件缺陷。

---

## I — 方法论骨架 (Interpretation)

同一套测试像同一种农药：反复喷洒后，残留害虫产生抵抗力，探针不再触及新的错误类别。

螺旋/迭代开发中每圈复用同一批用例，最后“能发现的都发现了”，再跑也不会有新发现——绿条给人安全感，却对残留缺陷失效。

处方不是“再跑一遍旧套件”，而是不断编写不同的、新的测试，覆盖程序不同部分；自动化全绿尤其不能被误读为“没什么好找的了”。

---

## A1 — 典型应用 (Past Application)

### 案例 1: 螺旋模式多圈回归
- **问题**: 每一圈都用同一批测试接软件，几回合后发现率塌陷。
- **做法**: 命名为杀虫剂怪事，指出必须换新测、换部位。
- **结论**: 回归包含“进化测试设计”，不只是重跑。
- **结果**: 成为回归与自动化策略的核心警告。

### 案例 2: 90% 覆盖仍可能免疫
- **问题**: 覆盖率很高且未发现缺陷，是否等于质量很好？
- **做法**: 提示也可能是对现有测试免疫；新用例可能暴露余下区域大量缺陷。
- **结论**: 高覆盖 + 零发现 ≠ 证无；要增加新测试。
- **结果**: 把覆盖工具从“安心仪表”改回“发现盲区的线索”。

---

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 回归/CI 长期全绿，生产或探索测试仍爆缺陷。
2. 自动化套件多年不增用例，只维护脚本通过率。
3. 多轮迭代缺陷发现曲线平坦，怀疑“测不动了”。
4. 有人说“自动化都跑过了，不用再手工/探索了”。

### 语言信号 (用户的话里出现这些就应激活)

- "杀虫剂怪事 / pesticide paradox / 测试免疫"
- "回归全绿但生产还挂"
- "同一套用例反复跑 / 自动化全绿就没事了吗"
- "要不要换测试手法 / 写新用例"

### 与相邻 skill 的区分

- 与 `bug-cluster-heuristic` 的区别: 成群是“找到一个后附近加码”；杀虫剂是“旧探针失效要换新探针”。
- 与 `prove-presence-not-absence` 的区别: 证无是一般认识论；本 skill 给出绿测失效的具体机制与处方。
- 与 `risk-based-test-selection` 的区别: 风险选测决定本轮焦点；本 skill 要求焦点上的手法必须演化。

---

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **诊断是否免疫**
   - 检查：多轮结果几乎不变、套件长期不增、以自动化绿为唯一放行证据。
   - 完成标准: 给出“疑似免疫 / 不像免疫”的判断及依据。

2. **设计换手法清单**
   - 至少提出 3 类变化：新数据/边界、新状态路径、新环境或角色、探索式会话、改象限（黑↔白、静↔动）。
   - 完成标准: 有可执行的新测条目，而非“再跑一遍”。

3. **把新测接入回归策略**
   - 旧套件可保留作变更侦测；发现力依赖定期注入新测与轮换。
   - 完成标准: 用户同意“绿条 + 本期新测主题”的双轨放行。
   - 判停条件: 若问题是首次范围太大不知测什么，转 `risk-based-test-selection`。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 全新功能还没有任何基线用例——先设计用例，不是先谈免疫。
- 用户只是要字段边界取点表。
- 单次失败的 flaky 测试稳定性问题（根因是环境/同步，不是杀虫剂）。

### 常见失败模式

- 反复使用相同测试使软件具有抵抗力。
- “执行了全部自动化测试没有发现缺陷，就认为没有软件缺陷要找了”——仍是杀虫剂现象。
- 过分依赖自动化替代测试员判断。

### 适用边界与局限

- 自动化实践偏桌面/早期 Web 的录制回放与工具观；与今日测试金字塔、契约测试、CI 矩阵不完全同构，但“探针必须演化”仍然适用。
- 未系统讨论变异测试等现代对抗免疫的工程手段——可作当代补丁，不否定本原则。

### 容易混淆的邻近方法论

- 缺陷成群：注意力再分配 vs 探针种类更新。
- 等价类过度合并：分类过粗会漏缺陷，但是一次性设计问题，不是多轮免疫。
